## Why only `isTeacher` is unit-tested
The DB-backed functions (`getCurrentSchoolId`, `getMembership`, `requireMembership`, `requireTeacher`) have no unit test of their own; unit-testing them would mean mocking Drizzle's query builder, which asserts the mock reproduces the SQL rather than that the SQL is correct — the same reasoning `auth/tokens.test.ts` accepts for its recording stub, except there even a stub is judged worth it because the invalidate/consume ordering is easy to get wrong silently. Here the functions are one `select` and two redirects; the payoff isn't there. They ARE covered end to end: `apps/web/e2e/learn.spec.ts` drives `requireMembership`'s three branches (logged-out → login, non-member → `/backflip`, member → `/learn` shell) and `requireTeacher`'s cosmetic counterpart (teacher sees the Courses link) against a real seeded database.

## Two role axes, kept apart
`user.role` (`owner | admin | teammate`, `L2-DB-05`) gates `/backflip/*` — the operator console. `school_member.role` (`teacher | student`) gates `/learn/*` — the product. They live in different tables, are read by different modules (`@/app/_lib/auth/permissions` vs `@/app/_lib/school`), and neither function consults the other's role. A person can be a `teammate` in the console and a `teacher` in a school; changing one never changes the other. See `L2-SCHOOL-04`.

## Guard shape mirrors `requireCapability`, deliberately
`requireMembership()` reads `auth()` itself rather than taking a session, so every `/learn/*` page/action is a one-line call — same shape as `@/app/_lib/auth/guard.ts`'s `requireCapability`. The three-way branch (no session → login; session, no membership → console; membership → return identity) exists because "not a member" is not an error state for this deployment: every authenticated user can reach `/backflip`, so a non-member visiting `/learn` lands somewhere real instead of a dead end.

## `getCurrentSchoolId` is a lookup, not a chooser — and not the only thing multi-school touches
One `school` row exists today (seeded by migration). The function still queries rather than hardcoding the seeded id. But it is not true that this is "the one function that changes" for a second school: `getMembership`'s signature (one `schoolId` per user), `requireMembership`'s return shape (a single `schoolId`), and `/learn` routing (which assumes one membership) all change too. What genuinely doesn't change is the schema — `L2-SCHOOL-01`'s data model already supports more rows; adding a second school is new rows, not a migration. `L2-SCHOOL-06` extends the "resolve school via a helper, never a client-supplied id" rule to all school-scoped queries.

`getCurrentSchoolId()` and `getMembership()` independently `limit(1)`/pick-one from what could become multi-row results, and until this fix neither ordered its query — two arbitrary picks that happened to agree only because exactly one school row exists. `L2-SCHOOL-11` is the rule that keeps this from becoming a silent bug: school-scoped work in a membership context takes `schoolId` from the membership, never from a fresh `getCurrentSchoolId()` call; `getCurrentSchoolId()` is for pre-membership contexts only (today: the invite page, resolving a school before the invitee has a membership row). Both queries now order deterministically (`createdAt` asc, `id` asc tiebreak) so the pick is at least reproducible — but determinism is not the same as the two queries agreeing once a second school exists, which is why the membership-vs-lookup rule matters independently of the ordering fix.

## Gotcha: importing `@/app/_lib/school` pulls in the real `next-auth`
`@/app/_lib/school/index.ts` imports `@/app/_lib/auth`, which imports the real (unmocked) `next-auth`. `next@16.2.6` ships no `"exports"` map in its `package.json`, so next-auth's own `import { NextRequest } from "next/server"` (extensionless) fails once Vitest externalizes the dependency and Node's native ESM resolver tries to resolve it — `require` and Next's own bundler both probe file extensions for a legacy (no-`exports`) package; Node's ESM loader does not. `auth/auth-callbacks.test.ts` never hits this because it mocks `next-auth`'s default export before import.

`membership.test.ts` only needs `isTeacher`, which has no such dependency, so the fix is structural rather than a config change: `isTeacher` (with the role types) lives in `roles.ts`, a file with zero imports beyond its own types, and the test imports `@/app/_lib/school/roles` directly instead of the `@/app/_lib/school` barrel. A global `test.server.deps.inline: ["next-auth"]` in `apps/web/vitest.config.ts` was tried first and did work, but was rejected on review as broader than the problem required — it would route every test's `next-auth` import through Vite's resolver, not just this one, and the repo already had a narrower precedent (`vi.mock("next-auth", ...)` in `auth-callbacks.test.ts`) for keeping the real package out of tests that don't need it. Splitting the pure half out is narrower still: no mock needed at all, and any future client component that only needs `isTeacher`/`SchoolRole` can import `roles.ts` without dragging in `server-only`.

## `sendWelcomeEmail` call site: no `loginUrl` param
`sendWelcomeEmail` (`apps/web/app/_lib/email/send.tsx`) takes `{ to, name }` only — it builds `loginUrl` internally via `appUrl()` and always points at `/backflip/login`. `inviteMember` therefore calls `sendWelcomeEmail({ to: email, name })`, not `appUrl`/`loginUrl` directly; passing a `loginUrl` field would be an excess-property type error against that function's params object. This matches the existing call site in `apps/web/app/api/backflip/users/route.ts`.

## Invite flow verification
The manual pass below (dev db, no authenticated browser session) was superseded by `apps/web/e2e/learn.spec.ts`, added in `0a647c6`, which now drives the full round trip through a real browser against a seeded `backflip_test` database — including the two branches the manual pass couldn't reach:
- Non-owner (TEAMMATE) hitting `/backflip/school` bounces to `/backflip` — exercises the `canEditUsers` re-check inside `requireCapability("users.edit")`, not just the hidden nav link.
- Owner submits the invite form, the new row appears in the table with the chosen role, then re-submitting the same email with a different role updates that row in place (one row, new role) — the UI round trip and the idempotent re-invite, both through real form submission and page state, not a script against the db directly.

Original manual pass, kept for the record (ran by hand against the local dev db, `backflip-db` role `backflip`, before the e2e suite existed):
- `corepack yarn workspace web build` compiles `/backflip/school` (page, action, form) with no errors; route appears as `ƒ /backflip/school` in the route table.
- Logged-out `curl` to `/backflip/school` against a running dev server 307s to `/backflip/login?from=%2Fbackflip%2Fschool` — the edge gate covers this route the same as every other `/backflip/*` path.
- The `inviteMember` transaction body (find-or-create `user`, `onConflictDoUpdate` on `school_member`) was exercised directly against the dev db with a temporary script reproducing the exact logic: inviting `student@example.test` as `student`, then re-inviting the same email as `teacher`, left exactly one `school_member` row with `role = "teacher"` and `user.role = "teammate"` (confirmed via `psql`). Test rows were deleted afterward; the dev db is back to its pre-verification state (one `school` row, the seeded owner only).

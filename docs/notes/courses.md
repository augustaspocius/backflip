## Ownership proof shape
Every UPDATE/DELETE in `courses/_actions.ts` and `[courseId]/_actions.ts` follows the same two-part shape: resolve the teacher server-side first (`const teacher = await requireTeacher()`), then scope the mutating statement's own `WHERE` to the teacher's school — `and(eq(courses.id, id), eq(courses.schoolId, teacher.schoolId))` directly in `courses/_actions.ts` (the row itself carries `schoolId`); `inArray(<fk column>, <subselect filtered on schoolId>)` in `[courseId]/_actions.ts` (`deleteDeck`, `updateCard`, `deleteCard`), because a deck/card row has no `schoolId` column of its own to filter on directly. Both are deliberate over fetch-then-check (a preceding `SELECT`, compare `schoolId`, then an unscoped write): a single scoped `UPDATE`/`DELETE ... WHERE ... RETURNING` is one round trip with no window between the check and the write, and an empty `.returning()` array is the one signal needed to tell "not found" from "found but wrong school" apart — both report identically as "not found", so a teacher never learns whether an id belongs to a different school.

INSERTs (`createCourse`; `createDeck`, `createCard`) are the deliberate exception, not a lapse: there is no existing row for an INSERT's `WHERE` to constrain, so the only way to prove the parent (school, or course/deck) belongs to the teacher is a `SELECT` before the write. This was already true of `createCourse`; `createDeck`/`createCard` carry it for the same structural reason and each has a comment saying so, precisely so a future reader does not read the newer UPDATE/DELETE shape and "fix" the two INSERTs — or the reverse — into matching it.

## `schoolId` source, restated
`createCourse` and every scoped update/delete take `schoolId` from `requireTeacher()`'s return, never a second `getCurrentSchoolId()` call — the single most load-bearing rule carried over from the school domain's review (`L2-SCHOOL-11`, `docs/notes/school.md`). `getCurrentSchoolId()` has no caller in this file.

## Known repo-wide weakness: `String()` coercion ahead of schema validation
Every `formData.get(...)` in `_actions.ts` is wrapped in `String(...)` before `courseSchema.safeParse`. If a `File` is posted under a text field name (e.g. `title`), `formData.get("title")` returns a `File` object, `String(file)` coerces it to `"[object File]"`, and that string then validates as ordinary text instead of being rejected as the wrong input type. This is not specific to this task — it is the pre-existing convention used verbatim in `apps/web/app/backflip/(protected)/users/_actions.ts`, `apps/web/app/backflip/(protected)/school/_actions.ts`, and the auth actions, so it was kept here rather than deviated from for one module. Recorded here as a findable, repo-wide input-handling weakness for whoever decides to fix it everywhere at once (e.g. by checking `typeof value === "string"` before coercing).

## Fix round 1 (post-review)
Three findings, all fixed in the same commit as this note:
1. **2 MB cap was unreachable.** Next's server-action default body limit (1 MB) sat below `MAX_BYTES` (2 MB), so the framework rejected anything over 1 MB before `uploadCardImage` ran, and the teacher never saw the app's own message. Fixed by raising `experimental.serverActions.bodySizeLimit` to `"3mb"` in `apps/web/next.config.ts` — deliberately above, not equal to, `MAX_BYTES`, since the framework limit covers the whole multipart body and a 2 MB file plus form overhead can exceed a 2 MB ceiling. Both `next.config.ts` and `_upload-actions.ts` carry a comment that the two numbers must stay apart. This raises the body limit for every server action in the app, not only this one — accepted because every other action here posts small text fields.
2. **Nothing inspected the bytes.** An SVG/HTML file renamed to `foo.png` would have been stored and served as `image/png`, relying entirely on the repo-wide `X-Content-Type-Options: nosniff` header (`apps/web/next.config.ts`, a file this task otherwise never touches) to stop a browser from executing it. Fixed by adding `matchesFileSignature` to `uploads.ts` (magic-byte check against the claimed extension, called from `uploadCardImage` before the file is written) and recording in `L2-COURSE-10` that `nosniff` is load-bearing for this defence, not decorative.
3. **A misleading test, and an untested real layer.** The original `..%2F..%2Fpackage.json` case in `uploads.test.ts` only passed because the literal `..` substring survives encoding — it never proved what the route receives in production (Next decodes route params first), and nothing tested the route itself. Fixed by relabeling that unit test as a defense-in-depth check (comment updated) and adding `route.test.ts`, which calls `GET` directly with a crafted `params` promise — the actual reproduction of the brief's curl check — covering traversal, a path separator, an unknown extension, a null byte, and the no-session case.

## Fix round 2 (final whole-branch review)
Seven findings from a review of the whole `feat/repeat-and-learn-authoring` branch, all fixed in this fix wave:

1. **`UPLOAD_DIR=` (empty string) defeated its own `??` default.** `??` only falls back on `undefined`, not `""`, and both example env files shipped the key assigned-but-empty — a plain `cp .env.example .env` produced `UPLOAD_DIR=""`, `mkdir("")` throwing ENOENT on the first upload. Fixed: `process.env.UPLOAD_DIR?.trim() || <default>` (same pattern as `telemetrySalt()`), plus both example files now ship the key fully commented out rather than assigned-empty, and a dedicated unit test (`describe("UPLOAD_DIR", …)`, using `vi.stubEnv` + `vi.resetModules()` + dynamic `import()` since the value is a module-level `const`) covers unset/empty/whitespace/real-override.
2. **Six server actions had zero UI callers**: `updateCourse`, `deleteCourse`, `deleteDeck`, `updateCard`, `deleteCard`, `unenrollStudent`. All correct on auth, none reachable from any control — an authoring tool that could create but never edit or delete. Wired minimally: `CourseHeader` gained an inline title/description editor (`updateCourse`) and a delete button (`deleteCourse`) gated by `window.confirm` — the one confirmation added anywhere in this round, because this is the one delete that cascades through every deck/card/enrolment with no undo; `DeckList` gained a per-deck delete (`deleteDeck`, no confirmation — smaller blast radius); the deck page's card list moved into a new `CardRow` component with an inline edit (two `Textarea`s + save, reusing `cardSchema` via `updateCard` itself) and delete (`deleteCard`, no confirmation); the roster page gained a per-student `UnenrollButton` (`unenrollStudent`, no confirmation — re-enrolling resumes the student's `card_state`, so this is recoverable).
3. **The deck page ignored its own `courseId`.** `and(eq(decks.id, deckId), eq(courses.schoolId, teacher.schoolId))` proved the deck's *school*, never that it belonged to the *course* named in the URL — a deck from a different course in the same school rendered under the wrong course's URL. Fixed by adding `eq(decks.courseId, courseId)` to the same `WHERE`. Recorded as a new invariant bullet under `L2-COURSE-11` in the contract. `apps/web/e2e/authoring.spec.ts` gained a same-school case (two courses, each with a deck, both owned by `OWNER`) asserting deck B renders under its own course's URL (200) and 404s under course A's URL — the existing cross-school tests never exercised this narrower same-school case.
4. **`card_state` assumptions recorded in `L2-COURSE-08`** while still fresh, ahead of plan 3: `unenrollStudent` deliberately orphans `card_state` (so re-enrolling resumes rather than resets) and `deleteCourse` assumes a cascade will clean `card_state` up (it never touches that table itself). Plan 3 is now bound, in the contract, to (a) give `card_state` a cascading FK to `card`, or course deletion silently orphans scheduling rows, and (b) join every review/scheduling query through `enrollment`, since `card_state` rows outlive an enrolment by design.
5. **Upload lifecycle bound stated in `L2-COURSE-10`**: `uploadCardImage` takes no deck/card id, so nothing links a stored file to a row — deleting a card/deck/course never deletes its images, and there is no quota or rate limit. Recorded as an accepted bound for a teacher-only, low-volume surface, with the two conditions that retire that acceptance: upload access widening past teachers, or storage pressure on the deploy target.
6. **Unified the client action-result convention.** Six components split three ways: two rendered both outcomes inline, three rendered failure only (silently discarding "Deck added."/"Student enrolled." on success), and `ImageUpload` split a third way again. Replaced with one shared `@/app/learn/_components/action-message.tsx` (`<ActionMessage state={...} />`, `L2-COURSE-11`), used by every one of the original six plus every control added in finding 2. Recorded as the standing convention in `L2-COURSE-11` and this file, so the next form does not invent a fourth.
7. **Two small ones.** `CardEditor`'s `front` field was controlled and never cleared on success (`back` was uncontrolled and happened to reset itself); both are now controlled and cleared together via a `useEffect` on `state?.ok`. `authoring.spec.ts`'s hostile-enrolment test waited on `page.waitForLoadState("networkidle")` before injecting a DOM option — a blind, untargeted proxy for "hydration is done" that could still flake on a slower machine; replaced with `await expect(async () => { await page.evaluate(inject, id); await expect(injectedOption).toHaveCount(1) }).toPass()`, which retries the injection itself until it survives hydration, deterministically.

- `apps/web/app/learn/courses/[courseId]/_actions.ts` — deck and card authoring server actions: `createDeck`, `deleteDeck`, `createCard`, `updateCard`, `deleteCard`. `requireTeacher()` first, `schoolId` from its return only, same as `courses/_actions.ts` — but a deck/card id has no `schoolId` column of its own, so proving ownership takes a join rather than a flat `WHERE`. Two different shapes, by necessity of SQL rather than choice:
  - `deleteDeck`, `updateCard`, `deleteCard` (UPDATE/DELETE, an existing row to scope) — the mutating statement is self-scoping: the ownership check lives *inside* its own `WHERE`, as `inArray(decks.courseId, db.select({ id: courses.id }).from(courses).where(eq(courses.schoolId, teacher.schoolId)))` (`deleteDeck`) or the two-level version scoping `cards.deckId` against a `decks ⋈ courses` subselect filtered on `schoolId` (`updateCard`/`deleteCard`). `.returning()` is the only "did this match a row I'm allowed to touch" signal; an empty array is always "Deck not found."/"Card not found." — a deck or card id from another school is indistinguishable from a nonexistent one, same property `courses/_actions.ts` has. There is no separate `SELECT` before the write and no window between check and write — see "Ownership proof shape" below, now shared verbatim by both action files.
  - `createDeck`, `createCard` (INSERT, no existing row to scope) — a `SELECT` proving the parent (course, or deck→course) belongs to the teacher's school runs *before* the `INSERT`, because an `INSERT` has no row of its own for a `WHERE` clause to constrain; there is nothing to self-scope. This is the one place a preceding check is unavoidable, not a shortcut around the rule above — both actions carry a comment saying so, so a future reader does not "fix" `deleteDeck`/`updateCard`/`deleteCard` back into this shape, or ask why `createDeck`/`createCard` don't match it.
  - `revalidatePath` needs the course id, which the self-scoping DELETE/UPDATE in `deleteDeck` gets for free (`decks.courseId` is a plain column, returned directly). `updateCard`/`deleteCard` only get `cards.deckId` back from their scoped write, so both resolve `courseId` with one more plain `SELECT` *after* the mutation has already succeeded — deliberately unscoped by school, because path revalidation is not a security check and gates nothing; the security proof already happened in the write above it.

## Ownership proof shape
Every UPDATE/DELETE in `courses/_actions.ts` and `[courseId]/_actions.ts` follows the same two-part shape: resolve the teacher server-side first (`const teacher = await requireTeacher()`), then scope the mutating statement's own `WHERE` to the teacher's school — `and(eq(courses.id, id), eq(courses.schoolId, teacher.schoolId))` directly in `courses/_actions.ts` (the row itself carries `schoolId`); `inArray(<fk column>, <subselect filtered on schoolId>)` in `[courseId]/_actions.ts` (`deleteDeck`, `updateCard`, `deleteCard`), because a deck/card row has no `schoolId` column of its own to filter on directly. Both are deliberate over fetch-then-check (a preceding `SELECT`, compare `schoolId`, then an unscoped write): a single scoped `UPDATE`/`DELETE ... WHERE ... RETURNING` is one round trip with no window between the check and the write, and an empty `.returning()` array is the one signal needed to tell "not found" from "found but wrong school" apart — both report identically as "not found", so a teacher never learns whether an id belongs to a different school.

INSERTs (`createCourse`; `createDeck`, `createCard`) are the deliberate exception, not a lapse: there is no existing row for an INSERT's `WHERE` to constrain, so the only way to prove the parent (school, or course/deck) belongs to the teacher is a `SELECT` before the write. This was already true of `createCourse`; `createDeck`/`createCard` carry it for the same structural reason and each has a comment saying so, precisely so a future reader does not read the newer UPDATE/DELETE shape and "fix" the two INSERTs — or the reverse — into matching it.

## `schoolId` source, restated
`createCourse` and every scoped update/delete take `schoolId` from `requireTeacher()`'s return, never a second `getCurrentSchoolId()` call — the single most load-bearing rule carried over from the school domain's review (`L2-SCHOOL-11`, `docs/notes/school.md`). `getCurrentSchoolId()` has no caller in this file.

Only `course-validation.test.ts` (the three schemas, which also cover `deckSchema`/`cardSchema`) is tested. `createCourse`, `updateCourse`, `setCourseStatus`, `deleteCourse`, `createDeck`, `deleteDeck`, `createCard`, `updateCard`, `deleteCard`, and now `enrollStudent`, `unenrollStudent` have zero tests today — the auth gate (`requireTeacher()` rejecting a non-teacher/non-member), the not-found messaging, and above all the cross-school isolation are all **unproven**, not merely untested-but-obviously-fine. This applies with extra force to `enrollStudent`: it is the one place in this domain guarding a hazard the database itself cannot (`L2-DB-44` hazard 2, `enrollment` has no `schoolId`), so its cross-school check — a course from school A, a student from school B — is exactly the kind of thing that must be exercised against a real second school, not just read as correct. Unit tests can't close this gap here — Vitest has no database or session in this harness, and proving isolation needs a second `school` row plus a second teacher membership. A dedicated end-to-end task later in this plan covers it.

## Known repo-wide weakness: `String()` coercion ahead of schema validation
Every `formData.get(...)` in `_actions.ts` is wrapped in `String(...)` before `courseSchema.safeParse`. If a `File` is posted under a text field name (e.g. `title`), `formData.get("title")` returns a `File` object, `String(file)` coerces it to `"[object File]"`, and that string then validates as ordinary text instead of being rejected as the wrong input type. This is not specific to this task — it is the pre-existing convention used verbatim in `apps/web/app/backflip/(protected)/users/_actions.ts`, `apps/web/app/backflip/(protected)/school/_actions.ts`, and the auth actions, so it was kept here rather than deviated from for one module. Recorded here as a findable, repo-wide input-handling weakness for whoever decides to fix it everywhere at once (e.g. by checking `typeof value === "string"` before coercing).
